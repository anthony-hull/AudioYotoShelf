# Mutation testing

[Stryker.NET](https://stryker-mutator.io/docs/stryker-net/introduction/) changes the source one small way at a
time (flips a `>` to `>=`, deletes a statement, swaps `Min` for `Max`) and re-runs the tests. A test suite that
still passes has not noticed the change: that is a **surviving mutant**, and it points at a missing assertion.

**Read the "Do not mutation-test this" section before running Stryker or spending time on a survivor.** It lists
what is excluded, what cannot be mutated, and what only looks like a gap. Each entry cost real time to find.

## Running it

Stryker is pinned in `dotnet-tools.json`. The SDK is in `~/.dotnet` for local work (`export PATH=$HOME/.dotnet:$PATH`).

```bash
dotnet tool restore

# 1. The gate for the pure logic in Core. ~40-60 s. Run this while working on Core.
dotnet stryker --config-file stryker-config.core.json

# 2. Everything, with a ratcheted floor. ~2.5-3.5 min on 20 cores.
dotnet stryker

# 3. One project or one file while iterating (faster than either of the above)
dotnet stryker --config-file stryker-config.json --mutate '**/TrackPlanner.cs'

# Read the result. Stryker's console table wraps into unreadable columns; the JSON does not.
python3 scripts/mutation-summary.py --survivors
```

Reports land in `StrykerOutput/` (git-ignored): `reports/mutation-report.html` for browsing,
`mutation-report.json` for scripts.

## The two gates

| Config | Scope | Break below | Baseline (2026-09-20) | Why |
|---|---|---|---|---|
| `stryker-config.core.json` | `AudioYotoShelf.Core` | **95%** | 99.58% | Pure logic (card limits, track planning, age suggestion, token validity). Unit tests are the right instrument here, so the bar is high. |
| `stryker-config.json` | whole solution, unit tests only | **60%** | 63.93% | A floor against decay. Most of `Infrastructure` and `Api` is reached only by integration tests (see below), so a high bar would be false precision. |

**Ratchet, never loosen.** When a change raises a score, raise `break` to just under the new score in the same
PR. Lowering `break` needs a written reason in `DECISIONS.md`.

The whole-solution baseline before the Core tests were added was 32.13% (Core 67.57%).

## Do not mutation-test this

### 1. Excluded in `stryker-config.json` (`mutate` globs)

These produce mutants that no unit test can meaningfully judge. Do not remove an exclusion to "improve
coverage", and do not write tests to kill mutants in them.

| Glob | Why it is excluded |
|---|---|
| `!**/Migrations/**` | Generated by EF Core (about half of `Infrastructure`'s lines). Regenerated, never hand-edited. |
| `!**/Program.cs` | Composition root: DI, middleware order, auth cookie wiring. Only the integration suite (`AuthIntegrationTests`) runs it for real. |
| `!**/Data/Configurations/**` | EF entity mappings. All 69 mutants survived because nothing but a real database can check them, and the integration suite applies the migrations. |
| `!**/Data/AudioYotoShelfDbContext.cs` | Same: model wiring, exercised by migrations and integration tests. |
| `!**/Observability/**` | Metric instrument registration. Nothing to assert on beyond "the endpoint exists". |

If you add a file of the same kind (another EF configuration, another registration class), add its glob and a
row here in the same commit.

### 2. Stryker cannot mutate these methods

Stryker's "Safe Mode" drops every mutant in a method it cannot recompile, and reports them as compile errors:

- `FfmpegChapterExtractor.ConcatenateAsync`
- `PlaylistTransferOrchestrator.TransferPlaylistAsync`

They are **not** mutation-tested at all, and no test change will alter that. Their safety rests on their
ordinary unit tests and review. Do not hunt for survivors there; there are none to find. (The run logs
`Safe Mode! Stryker will remove all mutations in <method>`; check that list after upgrading Stryker, it may shrink.)

### 3. `NoCoverage` in code that only integration tests reach

Stryker here runs the three **unit** test projects. The Testcontainers suite (`IntegrationTests`) is deliberately
left out, so anything only it exercises reports `NoCoverage` or `Survived` even though a test does check it.

- Measured example: `AuthController.cs:141` (`requested is null || ...`, the server-URL lock) survives the unit-only
  run, and is checked by `ApiKeyConnect_WithConfiguredServer_ConnectsToThatServer`.
- Why the integration suite is not fed to Stryker: it starts real Postgres and Redis containers, and Stryker
  restarts the test process for many mutants, in parallel. That is expected to cost far more than it returns.
  **This was reasoned, not measured.** If you want to disprove it, time one integration run under
  `--concurrency 1` first.

So a low score on `AuthController`, `TransfersController`, `YotoService` or `TransferOrchestrator` is a statement
about unit-test depth, not proof of an untested behaviour. Check the integration tests before writing a duplicate.

### 4. Equivalent mutants (cannot be killed by any test)

Some mutants do not change behaviour, so a survivor there is not a missing test. Mark the line with a comment that
gives the reason, and move on:

```csharp
// Stryker disable once Equality : `>` vs `>=` differs only when the expiry equals the current tick
```

Rules for the comment: name the mutator (`Equality`, `Linq`, `Arithmetic`, `String`), always give the reason after
the colon, and use `once` (never `disable all`). A `disable` covers the whole next statement or member, so do not
use it where it would also hide a killable mutant.

Known equivalents (all commented in source, except the last):

- `AgeSuggestionService`: `First()` on a list that always holds the duration signal; the `Math.Clamp` lower bound
  (every rule is at least 3 years wide, so it never binds); the `?? ""` fallback text (only has to be keyword-free).
- `UserConnection.HasValidYotoConnection`: the `>` against the live clock.
- **`UserConnection.HasValidAbsConnection` (line 60): left unannotated on purpose.** It is the same clock
  comparison, but a `disable Equality` on that property would also hide the killable `is null` mutant in it. It is
  the single remaining Core survivor.

### 5. Noise that is not worth killing

- **Log calls.** Ignored via `ignore-methods` (`Log*`, `ConfigureAwait`). Do not assert on log text.
- **Code with no logic.** DTO records, entities without behaviour, interfaces and enums produce zero mutants.
  Files showing `0` in the report are not gaps.
- **User-facing message text.** Assert it only where it carries computed values (`CardCapacityCalculator` messages
  do, and are tested). A string mutant on a fixed error sentence is not worth a brittle assertion.

### 6. Not covered yet

- **The Vue front end** (`src/AudioYotoShelf.ClientApp`) has no mutation testing. StrykerJS with the Vitest runner
  is the tool if it is wanted; it is a separate decision, not a gap in this setup.

## Choosing where to spend effort

Highest return first: **Core**, then pure helpers in `Api`/`Infrastructure` that already have unit tests
(`Validators.cs` 64.9%, `AbsTokens.cs` 80%, `PlaylistCapacity.cs` 20%), then the rest. Measured on 2026-09-20,
survivors worth a look in `Api`: the ownership filters `t.UserConnectionId != ...` in `TransfersController`
(lines 29, 73), `CardsController` (46) and `LibrariesController` (119). A test that fails when the filter flips
is what proves one user cannot see another's transfers.

## Runtime facts (one machine, 20 cores, 2026-09-20)

| Run | Mutants tested | Time |
|---|---|---|
| Core only | ~240 | 40-60 s |
| Whole solution | ~1,030 | 147-211 s |

GitHub-hosted runners have 4 cores, so expect roughly 4-5x longer in CI (an estimate from core count, not measured).
Run Stryker against a **green** suite only: a test that already fails proves nothing about a mutant.
